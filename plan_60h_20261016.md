## GOTCHA — always use a fresh session name on restart (2026-10-16 18:17)

Killing a controller and relaunching it with the SAME ws_session name fails: marimo renames a session
when it reconnects, so the controller's --session id goes stale and `configure()` returns nothing,
giving "configure failed -> abort" even though the sandbox is healthy (HTTP 200).

Restart recipe, whether or not the sandbox changed:
1. `pkill -f "ws_session.py sb-<id>"`
2. bump SESSION in the controller (jak3mut2 -> jak3mut3, etc.)
3. start ws_session.py with the new name, wait ~10 s
4. relaunch the controller

Symptom to recognise: "configure failed -> abort" within ~4 minutes of a restart, with /health = 200.

## Failure mode 3: kernel wedged while the sandbox is healthy (2026-10-16 19:35)

Symptom: `configure failed -> abort`, /health returns **200**, and a bare connect test
(`execute-code.sh -c 'print(1)'` with no --session) returns "Execution did not complete: the server
ended the stream without a result". The sandbox is alive at the HTTP level but the marimo kernel is
not answering. Seen after killing and relaunching a controller twice on the same sandbox.

Diagnosis order when a controller aborts:
1. `/health` != 200  -> sandbox died, duplicate and recover (failure mode 1)
2. `/health` == 200 and a bare connect test WORKS -> stale session name (failure mode 2): bump SESSION
3. `/health` == 200 and a bare connect test HANGS -> kernel wedged: the sandbox is unusable.
   Shut the notebook down from the list, then REOPEN THE SAME NOTEBOOK - that starts a fresh sandbox
   and avoids creating yet another copy (there are already 154).

**Also:** a wedged notebook still counts toward the 2-notebook limit, and the list can show a stale
"Running" badge for ~1 min after shutdown. Confirm with /health == 410 before duplicating or opening
anything else, or molab will silently kill the other live run.
